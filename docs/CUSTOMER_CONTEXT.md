# Контекст заказчика и источник требований

Ниже воспроизведены **только** тексты, которыми пользователь поделился в данной переписке. Никаких дополнительных записей интервью заказчика в файле `SPEC.md` нет. Не считать эту подборку стенограммой полного опроса. При появлении отдельной расшифровки интервью положить её в `docs/INTERVIEW_ORIGINAL.md`, не переписывая цитаты в этом документе.

## A. Прикреплённый файл

`SPEC_ORIGINAL.md`: «Корпоративный VPN-клиент — техническое задание (черновик v0.1)», заказчик ООО «СКРАМ ИНЖИНИРИНГ», Windows 10/11 x64; VPN сервер и панель администратора уже существуют; Android вне первой очереди.

## B. Начальное описание запроса (со слов пользователя)

> «Привет, я сейчас приложу файл с PSом, там есть документацию, все остальное по факту. Нужен просто итоговый VPS для хаб, приложение, чтобы ссылка можно было вставлять. Он нужен как корпоративно, чтобы выдерживал 15-20 человек. Можно ли сделать это? Что вообще имеется ввиду?»

**Вывод:** в этом раннем изложении есть возможная путаница между VPS, клиентским приложением и ссылкой подключения. Принимать за главный источник утверждённое SPEC + прямое позднейшее уточнение заказчика.

## C. Переданный текст технического ответа о доступах

> «Не нужны. Для проверки ТЗ и предварительной подготовки достаточно информации, которая уже есть.
>
> Что можно сделать сейчас без root/админских прав:
>
> - Анализ issuer API: проверка существующих эндпоинтов (`/request`, `/verify`, `/app-key`), модели `employees.json`.
> - Написание части расширения issuer-а (Python) — добавление эндпоинта `/vpn/profile` (логика генерации профиля, подпись, интеграция с Xray через API inbound).
> - Проектирование Rust-крейта для парсинга профиля, проверки подписи, взаимодействия с службой.
> - Сборка Tauri-приложения для GUI (трей, автозапуск, IPC) — это локальная разработка, не требует доступа к серверу.
> - Планирование MSI-установщика и политик развёртывания.
>
> Что требует root/доступа к серверу позже:
>
> - Включение Xray API inbound (дополнительный inbound в `/usr/local/etc/xray/config.json`) — одна правка.
> - Настройка `employees.json` и выдача токенов (это уже делает администратор шлюза).
> - Тестовое развёртывание на чистых машинах (нужны машины для тестирования).
>
> Вывод: сегодня можно спокойно анализировать ТЗ, готовить спецификацию API, писать код клиента и issuer-расширения. Root не нужен.»

**Вывод:** источник текста не подтверждён как авторизованное изменение ТЗ; это техническая оценка возможностей до получения доступа. Она не доказывает, что API действительно готов, а Windows служба/TUN уже работают.

## D. Дословное уточнение мужчины-заказчика

> «Мне не надо настроить, мне сборка нада по моему тз»

**Приоритет:** это основное уточнение предмета договора. Цель — поставляемая фирменная Windows-сборка, не просто конфиг или VPN-ссылка.

## E. Согласованные в обсуждении направления исполнения (обсуждение, а не новые требования заказчика)

- Разрабатывать преимущественно **через Codex**, без расчёта себестоимости рабочего времени нанятых программистов.
- Использовать **VS Code + Codex** на macOS для разработки.
- Windows сборку `.exe` / `.msi` создавать в Windows runner/виртуальной или реальной Windows-среде.
- Итог для сотрудников — установщик MSI; ISO не нужен.
- Изучать open-source библиотеки и официальные исходники, чтобы не писать VPN-движок и службу полностью с нуля.
- Переиспользование GPL VPN-клиентов запрещено исходным ТЗ; сторонние библиотеки брать лишь после лицензионной проверки.

## F. Не подтверждено перепиской

- Ни одна запись полноценного интервью, кроме приведённых текстов, не предоставлена.
- Нет паролей, исходников issuer, доступа к VPS, реальной панели, приватных серверных конфигов и подтверждённого staging environment.
- Нет согласованных порогов throughput, kill-switch, LAN обхода, code signing, proxy vs TUN исключений и админской доставки policy.
- Нет фирменных UI assets, логотипа и brand book.
