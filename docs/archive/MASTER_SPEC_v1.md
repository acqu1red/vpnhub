## 0. Цель, тип заказа и приоритет источников

### 0.1. Что строим

[ИСТОЧНИК] Требуется **готовая сборка собственного фирменного VPN-клиента**, а не обычная настройка чужого клиента или новый VPS. Последняя прямая формулировка заказчика: «Мне не надо настроить, мне сборка нада по моему тз». Для 15–20 корпоративных пользователей требуется клиент Windows с одной кнопкой «Подключить», входом сотрудников, управляемыми с сервера настройками и отзывом доступа по устройствам.

[ИСТОЧНИК] VPN-сервер и административная панель уже существуют и в исходном ТЗ объявлены **вне объёма создания с нуля**. Однако то же ТЗ требует небольшое, но обязательное **расширение** существующего issuer/API и Xray API-inbound. Не трактуй «сервер вне объёма» как «сервер нельзя изменять никогда»; трактуй как «не создавать новую серверную платформу, делать только явно согласованные интеграционные правки».

[ИСТОЧНИК] В первоначальном пояснении упомянуты «итоговый VPS для хаб, приложение, чтобы ссылка можно было вставлять» и нагрузка 15–20 сотрудников. Формулировка не является полноценным продуктовым требованием и расходится с позднейшим «нужна сборка по ТЗ»; **никакой импорт произвольной VPN-ссылки в пользовательском интерфейсе по умолчанию не добавлять**, потому что по SPEC профиль выдаётся централизованно и настройки пользователю недоступны. Отдельно запросить подтверждение, нужен ли deep-link/корпоративный enrollment-link в будущем.

### 0.2. Приоритет документов при разногласиях

1. Последующие **письменно утверждённые** решения заказчика в `docs/DECISIONS.md`, если они есть.
2. Исходное `SPEC_ORIGINAL.md` как базовые требования.
3. Прямая переписка с заказчиком в `docs/CUSTOMER_CONTEXT.md` как уточнение типа результата.
4. Этот `CODEX_MASTER_SPEC.md` как инженерная декомпозиция.
5. Примеры GitHub — только справочные источники, а не источник требований.

Если пункты 1–4 противоречат друг другу, фиксируй конфликт в `docs/OPEN_DECISIONS.md`, не «угадывай правильный ответ». Для безопасной автономной работы допускается проектировать интерфейсы, писать макеты API и тесты; **не подключать реальную продуктивную инфраструктуру и не включать опасные функции до решения блокера**.

### 0.3. Определение «готово»

Готовый продукт — это **не** успешный `cargo build`, не кликабельная кнопка и не мокап. Это корректно подписанный (после приобретения заказчиком соответствующего сертификата) или честно обозначенный как тестовый установщик Windows, который устанавливает службу и зависимости, подключает действующего сотрудника к реальному VPN, направляет требуемый трафик по туннелю, применяет профиль, обеспечивает отзыв, корректно восстанавливает сеть после отключения/аварии, имеет тесты и документацию. Если нет сертификата или доступа к серверу, допускается **candidate build**, но не коммерческая приёмка.

## 1. Скоуп и нефункциональные требования

### 1.1. В первой очереди ОБЯЗАТЕЛЬНО

- Windows 10/11 x64; отдельный системный сервис под учетной записью `LocalSystem`/SYSTEM.
- GUI на Tauri 2 с фирменным названием **ScrumeVPN**, главным действием «Подключить/Отключить», статусом соединения, входом, сменой учётки, выходом, треем; без пользовательского экрана сетевых настроек.
- Одна логика состояния подключения, одинаково видимая в окне и в трее.
- Windows service: lifecycle VPN-движка, проверка политики и профиля, настройка сетевого туннеля, обработка ошибок/перезапуска.
- Обмен GUI ↔ service через Windows named pipe, versioned JSON-RPC или эквивалентный строго описанный протокол; доступ на основании SID и ACL.
- Использование существующих `/request`, `/verify`, `/app-key`, `/revoke` и добавление `/vpn/profile` по согласованному контракту.
- Токен устройства (`at-…`) хранится с DPAPI, не в plaintext; session (`as-…`) короткоживущая и только в памяти; секрет `sk-…` не выводится пользователю, не записывается в логи и не используется в VPN-клиенте.
- Подписанные Ed25519 профиль и серверная политика; валидация ДО любого применения.
- Генерация конфигурации Xray из проверенного профиля; VLESS + REALITY, XTLS Vision, TCP; TUN Wintun на Windows.
- Отзыв профиля администратором и удаление клиентского UUID на стороне Xray без разрыва соединений других сотрудников, при условии поддержки серверного API.
- Переносимое бизнес-ядро на Rust без прямой зависимости от Windows-API и отдельные Windows-адаптеры.
- MSI (WiX), GPO/Intune deployment-readiness, установка/обновление/удаление, минимальные права GUI.
- Базовый набор тестов, ручная матрица E2E, документация сборки и эксплуатационная инструкция.
- Возможность эксплуатации 15–20 сотрудников как **приёмочное испытание под реалистичной нагрузкой**, не просто декларация.

### 1.2. НЕ входит в первую очередь

- Разработка нового VPS/VPN-шлюза с нуля; замена существующего admin UI.
- Android, iOS, macOS/Linux-клиенты; отдельная мобильная сборка.
- Личный кабинет, платёжная система, мультиарендность, магазин подписок.
- Произвольный импорт `.vless` ссылок обычным сотрудником, редактор DNS/портов/серверов.
- Собственный VPN-протокол, собственный сетевой драйвер, форк Xray без необходимости.
- Автоматическое обновление с сервера, если не утверждены канал распространения, подпись и rollback-policy (можно спроектировать интерфейс).

### 1.3. Качество, ограничения

- Приоритет: безопасность и предсказуемое сетевое поведение > скорость разработки > декоративные элементы.
- Никаких заявлений «неубиваемая защита от локального администратора». Локальный администратор может отключить сервис, изменить бинарники и наблюдать за машиной; источник контроля — серверная выдача/отзыв.
- Не обещать абсолютное отсутствие утечек DNS или IPv6 до реальной проверки.
- Не обещать размер `~10 МБ` **всего установщика**: в исходном ТЗ такая оценка относится к оболочке, а Xray + Wintun увеличат пакет. Размер измерить после сборки.
- Поддерживать офлайн-сценарии только согласно согласованному времени истечения/политике — не обходить отзыв «последней хорошей копией» бесконечно.
- Уточнить Windows 10: 14.10.2025 закончилась стандартная поддержка; возможны ESU/LTSC и исключения — формализовать корпоративную политику.

## 2. Исходные технические сведения о текущем окружении

**Сведения из чернового ТЗ — НЕ проверены доступом к серверу.**

- Платформа issuer: Python, файл `/opt/llm-gateway/issuer/gw_issuer.py`; внутренний порт 4100; внешнее имя `gw.ailabscrume.ru` через nginx.
- Сотрудники: `employees.json`; разрешены `scrume.ru`, `mashkancev.ru` и одно исключение; отсутствие сотрудника означает отказ.
- Xray на сервере: inbound `vless-reality`, TCP `8443`, `xtls-rprx-vision`; текущий REALITY dest `www.samsung.com:443`, `serverNames` включают `www.samsung.com`/`www.cloudflare.com`; указано четыре уже имеющихся клиента. Эти данные нельзя публиковать или проверять на живом сервере без разрешения.
- В исходном примере профиля указан адрес VPN-сервера; реальное значение хранится в `SPEC_ORIGINAL.md` и **не должно хардкодиться в клиенте или демонстрационных тестах**. В новой документации использовать `vpn.example.invalid` или шаблон `${VPN_SERVER}`.
- Для динамического добавления/удаления пользователей предлагается Xray HandlerService по `127.0.0.1:10085` — **запрет выводить этот API наружу**.
- Требуется per-enrollment UUID (по конкретному устройству/зачислению, не один UUID на человека).

### 2.1. API — утверждено текстом оригинала, требует фактической проверки

```http
POST /request
Content-Type: application/json
{"email":"worker@example.invalid"}
```

```http
POST /verify
Content-Type: application/json
{"email":"worker@example.invalid","code":"123456"}
```

По исходному ТЗ: `{"ok":true,"key":"sk-…","install_token":"at-…"}`. **Критический конфликт:** одновременно сказано, что `sk-…` должен жить только на шлюзе. Codex не должен принимать `sk-…` как VPN-ключ, сохранять его, логировать или передавать через UI. Для чистого VPN-контракта требуется согласовать отдельный ответ/фильтрацию на серверной стороне; не менять старый endpoint несовместимо для остальных клиентов без явного согласования.

```http
POST /app-key
X-Install-Token: at-REDACTED
```

Ожидается `{ "access_token":"as-…", "expires_in":300 }`.

```http
POST /revoke
Content-Type: application/json
{"install_token":"at-REDACTED"}
```

Исходный `/revoke` доступен только на localhost сервера, то есть **обычный Windows-клиент его не вызывает**. Это операция администратора/внутреннего сервиса.

Новое расширение:

```http
GET /vpn/profile
X-Install-Token: at-REDACTED
```

Структура (пример без реальных данных):

```json
{
  "ok": true,
  "profile": {
    "protocol": "vless",
    "server": "vpn.example.invalid",
    "port": 8443,
    "uuid": "00000000-0000-4000-8000-000000000000",
    "flow": "xtls-rprx-vision",
    "tls": {
      "type": "reality",
      "sni": "www.example.invalid",
      "fingerprint": "chrome",
      "public_key": "EXAMPLE_NOT_A_KEY",
      "short_id": ""
    },
    "network": "tcp",
    "dns": ["1.1.1.1", "8.8.8.8"],
    "mtu": 1400,
    "split_tunnel": {"mode":"exclude","cidrs":[],"domains":[]}
  },
  "signature": "BASE64_SIGNATURE_PLACEHOLDER",
  "expires_at": "2027-01-01T00:00:00Z"
}
```

**НЕ копировать плейсхолдеры в рабочий Xray-конфиг.**

### 2.2. Дополнительные спецификации до правки сервера

1. `docs/API_CONTRACT.md`: точный URL, JSON Schema/OpenAPI, статусы `400/401/403/404/409/429/5xx`, лимиты, таймауты, ретраи, redaction, договорённость о versioning.
2. `docs/ISSUER_CHANGE_PLAN.md`: минимальные доработки Python, миграция `employees.json`, резервные копии, rollback, атомарное сохранение.
3. `docs/XRAY_API_PLAN.md`: динамическая регистрация/отзыв, уникальная email/alias метка на **зачисление**, проверка наличия пользователя, идемпотентность, восстановление state после рестарта Xray, аудит и автоматическое согласование реального состояния Xray с базой выдачи.
4. `docs/SIGNING_CONTRACT.md`: какие байты подписываются, алгоритм, codepoint/JSON каноникализация, `key_id`, сроки жизни, политика ротации, тестовые подписи.
5. `docs/SECURITY_BOUNDARIES.md`: trust boundaries сервер ↔ клиент ↔ SYSTEM ↔ GUI.

## 3. Предлагаемая архитектура (не менять без ADR)

```text
[Пользователь Windows, обычные права]
  ScrumeVPN.exe  (Tauri 2 + TS/Svelte или React; выбор фиксировать в ADR)
    ├─ экран email → код из письма / либо approved browser flow
    ├─ кнопка Подключить/Отключить, статусы, ошибки
    ├─ трей + запуск GUI при входе пользователя
    └─ Windows Named Pipe (JSON-RPC, SID/ACL, input validation)
                    │
                    ▼
[LocalSystem; Windows Service]
  ScrumeVPNSvc.exe  (Rust)
    ├─ lifecycle + IPC authorizer
    ├─ policy/profile verification (Ed25519)
    ├─ protected state and atomic file writes
    ├─ Xray config generator + process supervision
    ├─ TUN/DNS/routes/network rollback
    ├─ kill switch (только после решения OPEN-03)
    ├─ backoff, reconnect, health checking
    └─ telemetry/logs без ключей, кодов, DNS-трафика по умолчанию
                    │
                    ▼
  xray.exe + официальный Wintun DLL → Windows TUN → VLESS REALITY
                    │
                    ▼
[Сервер заказчика]
  nginx / existing issuer API → /vpn/profile → Xray HandlerService локально
```

### 3.1. Логическая декомпозиция Cargo workspace

- `crates/scrume-core`: типы профилей и политик, валидация, конечный автомат, абстрактные порты `IssuerApi`, `ProfileStore`, `TunnelController`, `Clock`.
- `crates/scrume-crypto`: Ed25519 verify, canonical JSON, envelope, key rotation.
- `crates/scrume-issuer-client`: HTTPS-клиент issuer (по возможности platform-neutral), token refresh и обработка ошибок.
- `crates/scrume-config`: безопасная генерация Xray-конфига с allowlist и тестовыми fixtures.
- `crates/scrume-windows`: DPAPI, Windows ACL, named pipe, защищённые файлы, реестр/права, route management, служба.
- `apps/service`: `ScrumeVPNSvc.exe` — только сервер Windows SCM, запуск/остановка Xray и системные операции.
- `apps/desktop`: Tauri 2 GUI + frontend, общается с service через минимальный набор команд; **не запускает Xray с правами пользователя в production**.
- `apps/issuer-extension`: отдельный пакет/патч для существующего Python issuer; не копировать всю инфраструктуру заказчика в публичный проект.
- `tests/`: contract tests, security tests, Windows E2E, fault injection, fixture data.
- `packaging/wix/`: доп. шаблоны WiX для установки/обновления/удаления службы, sidecars и ACL.
- `docs/`: ADR, API, установка, поддержка, тестовые отчёты, подтверждения лицензий.

### 3.2. Правила изменений архитектуры

- Запрещён запуск `xray.exe` непосредственно из Tauri WebView/JS в production; GUI не хранит raw-REALITY UUID в доступных фронтенду настройках.
- Критичные команды GUI выполняются только после проверки локального пользователя/SID/authorization; **не доверять** полю `user_sid` из самого JSON.
- Минимизировать поверхности с правами SYSTEM; доступ к сервисным файлам задаётся через Windows ACL, не только интерфейсом.
- Не выдавать персистентные ключи из службы GUI. Если UI необходима авторизация, передавать только значения, строго нужные на короткий срок; предпочтительна защищённая передача установки в службу.
- Безопасное восстановление сети и отсутствие зависших DNS/routes после crash входят в MVP, не оставлять «на потом».
- Параллельный запуск Xray в двух экземплярах и «двойной connect» не допускается.

## 4. UX/UI: экраны, состояние и tray

### 4.1. Разрешённые экраны

1. **Первый запуск/вход:** логотип ScrumeVPN, ввод корпоративного email, запрос OTP или запуск утверждённого браузерного механизма, ввод кода (если подтверждён именно email OTP), понятные ошибки.
2. **Главный экран:** текущая учётная запись (без лишних персональных данных), крупная кнопка «Подключить», индикатор состояния, диагностическая человекочитаемая ошибка, «Сменить учётную запись», «Выход».
3. **Трей:** Подключить/Отключить, Открыть, Выход. Значок меняется: подключено/отключено/в процессе/ошибка.
4. **Блокировки:** профиль истёк; устройство отозвано; сеть недоступна; требуется новая авторизация; служба не работает — отдельные понятные состояния.

**Не показывать:** UI конфигурации серверов, технический протокол, UUID, вставку произвольной VLESS-ссылки, публичный ключ REALITY, рекламные/чужие логотипы.

### 4.2. Состояния конечного автомата

`UNENROLLED → ENROLLING → AUTHENTICATED → PROFILE_FETCHING → READY → CONNECTING → CONNECTED → DISCONNECTING → READY`

Отклонения: `ERROR_RETRYABLE`, `ERROR_FATAL`, `REVOKED`, `EXPIRED`, `POLICY_INVALID`, `SERVICE_UNAVAILABLE`, `OFFLINE`, `UPDATE_REQUIRED` (если появится min client version), `RECOVERING_NETWORK`.

Разрешённые переходы описать тестами. Повторный connect идемпотентен. Кнопка во время перехода защищена от дубликата команд. После перезапуска GUI состояние читается из службы, а не локального store.

### 4.3. Поведение закрытия и автозапуска

- Закрытие окна → скрыть в трей, если служба работает; «Выход» → закрыть только GUI, поведение VPN согласно политике.
- Автостарт GUI при логине через HKCU/механизм Tauri; автозапуск SYSTEM-службы через SCM при старте ОС.
- Если `auto_connect=true` при старте ОС, service без GUI должна иметь **реально доступный** секрет; см. конфликт per-user DPAPI vs SYSTEM. **До решения этого конфликта автоподключение при загрузке не заявлять выполненным**.
- Визуальные бренд-ассеты брать только из материалов заказчика; пока их нет, neutral placeholders с явной меткой «заменить».

## 5. Безопасность, секреты, авторизация

### 5.1. Trust boundaries

| Граница | Требование |
|---|---|
| Интернет ↔ issuer | HTTPS с валидной цепочкой сертификатов, без `verify=false`; таймауты; минимальная информация в ошибках |
| Issuer ↔ клиент | Signed policy/profile, anti-replay, schema validation, anti-rollback |
| GUI ↔ service SYSTEM | Named pipe ACL, проверка identity через Windows token/SID, authorization на каждую команду |
| Service ↔ filesystem | ACL, atomic replace, отсутствие ключей в world-readable файлах |
| Service ↔ xray | Изолированный child process, запрет произвольных CLI args, проверка хэшей релизов |
| Issuer ↔ Xray API | localhost, ограниченная конфигурация, недоступно из внешней сети |
| CI ↔ secrets | Ни один prod token/ключ не загружается в GitHub Actions; отдельные mock fixtures |

### 5.2. Секреты и DPAPI — критический архитектурный выбор

[ИСТОЧНИК] `at-…` — per-user DPAPI; сервис работает от SYSTEM и стартует с ОС; туннель должен подниматься до входа GUI. **Это может быть несовместимо без дополнительного механизма.**

[ПРОЕКТНОЕ ПРЕДЛОЖЕНИЕ] Codex должен написать `docs/ADR-DPAPI-BOOT.md` с минимум тремя вариантами:

A) per-user DPAPI + подключение только после логина пользователя, без предлогинного auto-connect; сервис работает, но не поднимает туннель до логина;  
B) машинное защищённое хранилище/TPM/сертификат с service-only ACL, модель привязки к устройству и угрозы локального админа;  
C) разделение enrolment и секретов service/user с защищённой передачей и политикой ротации.

Не выбирать молча. Пока не решено — тесты на макете и безопасная заглушка для настоящих секретов.

### 5.3. `sk-…` из `/verify`

- В исходном ТЗ одновременно присутствуют возвращаемое поле `key: sk-…` и требование «ключ только на шлюзе». Нужен API-совместимый план: на VPN-flow сервер не должен выдавать сырой LiteLLM API-key, либо защищённо фильтрует/отдаёт другой ответ **по отдельно согласованному контракту**.
- До согласования валидировать наличие/тип поля ответа, **игнорировать и никогда не логировать** значение. Нельзя заявлять, что секрет фактически «остаётся только на шлюзе», пока сервер всё ещё возвращает его клиенту.

### 5.4. Подпись профиля и политики

- Ed25519; проверять подпись над **однозначно определённым** набором полей, а не произвольным «canonical JSON».
- [ПРОЕКТНОЕ ПРЕДЛОЖЕНИЕ] Стандарт каноникализации RFC 8785 (JCS) при поддержке идентичных тестовых векторов Python и Rust; явное `signature_version`, `key_id`, `issued_at`, `expires_at`, `enrollment_id`, привязка назначения `context="scrumevpn/profile/v1"`; signer и verifier должны подписывать одни и те же байты. Не считать этот формат утверждённым без решения.
- Протокол не должен допускать замены `expires_at` или policy_version без нарушения подписи.
- Проверять время, drift/clock skew, срок действия, pinned public key и при необходимости ротацию `key_id`; запрещать rollback на более старую конфигурацию после применения новой, кроме явной процедуры восстановления.
- Встроенный публичный ключ Ed25519 не является секретом; private signing key **никогда** не записывать в исходники, `.env`, GitHub Actions или бинарь клиента.
- При недействительной новой подписи использовать **последнюю валидную только пока она допустима по сроку и политике отзыва**, регистрировать ошибку; при сомнении блокировать новое подключение и вывести код ошибки.

### 5.5. Защищённый IPC

- Поименованный канал `\\.\pipe\ScrumeVPN\v1` либо допустимый для Windows эквивалент; проверить допустимость имени и DACL.
- На уровне транспортного соединения извлекать Windows identity клиента с защитой от impersonation/spoofing; разрешать только авторизованному интерактивному пользователю или approved admin/installer.
- Использовать строгий протокол: `protocol_version`, `request_id`, `method`, `params`; лимиты размера, длины, частоты команд, таймауты; ошибки без чувствительных данных.
- Минимальные методы: `status.get`, `auth.begin`, `auth.complete`, `profile.refresh`, `vpn.connect`, `vpn.disconnect`, `logs.export_redacted` (если утверждено), `account.switch`.
- `connect/disconnect` доступны только при валидной enrolment и политике; операция `logs.export` не выдаёт секреты; недокументированные privileged methods запрещены.
- Никаких raw shell commands из IPC или из параметров сервера. JSON/URL не превращаются в аргументы командной строки без allowlist.

### 5.6. Логи и аудит

- Структурированные события: время UTC, version, event_id, request_id, enrollment hash/pseudonym, status, duration, error code.
- Никаких OTP, `at-`, `as-`, `sk-`, UUID в открытом виде, приватных ключей, полномасштабных логов посещённых доменов по умолчанию.
- Защитить логи ACL и настроить rotation; предусмотреть безопасный экспорт для службы поддержки по согласованию.
- Серверные события revoke/create/refresh логировать независимо и с ограничением доступа.

## 6. Issuer, профиль, администратор

### 6.1. Enrollment workflow

1. GUI просит email.
2. Issuer `/request` отправляет 6-значный код (TTL 600 с, до 5 попыток, resend ≥60 с — как указано в исходном ТЗ; фактическое поведение подтвердить тестами).
3. Пользователь вводит код либо подтверждает вход в системном браузере — **метод должен быть согласован** (см. OPEN-01).
4. `/verify` создаёт/возвращает `install_token`.
5. Защищённое сохранение enrolment token в выбранную модель DPAPI/службы.
6. `/vpn/profile` возвращает per-device профиль; верификация Ed25519, schema, срок жизни и binding.
7. Xray outbound config генерируется строго из allowlisted данных, состояние = READY.
8. `Connect` → сервис поднимает TUN, применяет DNS/routes, запускает Xray, выполняет healthcheck, сообщает CONNECTED только после настоящего успеха.

### 6.2. Enrollment isolation

- Каждый `install_token` сопоставляется уникальному `uuid` и отдельному Xray client id / email alias; разные устройства одного сотрудника получают разные идентификаторы.
- Повторный `/vpn/profile` с тем же токеном **не должен** создавать дублирующих клиентов; нужна идемпотентность и транзакционность.
- Нельзя возвращать разные UUID для одного enrollment без специально согласованной операции ротации.
- В `employees.json` не допускать race/утери записи при параллельной выдаче 15–20 сотрудникам; если хранение JSON остаётся, необходим lock+atomic write+backup, либо обоснованная миграция на БД после утверждения.
- Отзыв должен убрать пользователя из авторизации **и** Xray; при частичном отказе — повторяемая операция + audit + reconciliation.

### 6.3. Revoke semantics / offline policy

[ПРОЕКТНОЕ ПРЕДЛОЖЕНИЕ] Разделить:

- `SUSPEND/REVOKED` — немедленный запрет на серверной стороне на новые соединения / отключение клиента по возможностям Xray; локальный клиент получает отказ при refresh, но без сети не может знать о событии.
- `PROFILE_EXPIRED` — локально запрещает новый туннель без валидного обновления.
- `APP_KEY_EXPIRED` — перевыпуск `as-…`, без бесконечного login loop.

**Не обещать мгновенный отзыв офлайн-клиенту без отдельного server push/polling / enforcement на шлюзе.** Персональные конфиги в статике нельзя оставлять активными после `/revoke`.

### 6.4. Политика администратора

Предполагаемые поля только после согласования: `version`, `auto_connect`, `kill_switch`, `refresh_interval_seconds` (default 21600, максимум 86400), `allow_lan`, `dns_mode`, `split_tunnel`, `max_profile_age`, `min_client_version`, `signature`.

- Изменение политик не доступно в GUI.
- Служба выполняет плановую проверку, при желании Admin trigger. Но **доставка команды из панели** не описана исходным ТЗ: оформить вариант (polling с version/ETag, websocket/notification, restart service) и договориться.
- Проверка на каждом старте, периодически каждые 6 ч по умолчанию, не реже 24 ч; использовать jitter/backoff, не штурмовать API одновременно 20 клиентами.
- Если политика невалидна, не применять её; последняя валидная копия лишь в согласованных рамках offline/expiry.
- Для source-of-truth нужно явно описать, где и как формируется `policy.json`: источник не задан в SPEC (см. OPEN-06).

## 7. Xray + REALITY + TUN и сеть

### 7.1. Движок

- Использовать **официальный** бинарный релиз `XTLS/Xray-core`; фиксировать точную версию и SHA-256, проверять артефакт из trusted source. Не скачивать latest при каждой пользовательской установке.
- Предпочтение архитектуре: **один экземпляр** Xray под контролем SYSTEM-службы; sidecar RustVPN годится как reference для config/tray, но не заменяет service isolation.
- Параметры профиля по исходному ТЗ: `vless`, `tcp`, `reality`, `flow=xtls-rprx-vision`, SNI, fingerprint, public_key, short_id, port, UUID, DNS, MTU, split tunnel.
- Сервис не должен доверять произвольным полям signed JSON как разрешению на запуск программ, выбор локального privileged port, dynamic arbitrary CLI и т. п.

### 7.2. TUN: сначала исследование возможностей встроенного Xray

[ВНЕШНИЙ ИСТОЧНИК] В Xray есть `tun` inbound с поддержкой Windows через официальный `wintun.dll`, в т. ч. опции маршрутизации/DNS в актуальном upstream; см. `https://github.com/XTLS/Xray-core/blob/main/proxy/tun/README.md` и `https://github.com/XTLS/Xray-docs-next/blob/main/docs/en/config/inbounds/tun.md`.

Задача Codex:

1. Проверить на **зафиксированном релизе Xray** действительно поддерживаемые Windows TUN опции, корректную конфигурацию и требования к правам.
2. Провести POC `Xray TUN` на тестовом Windows x64 **без production keys**; сначала доказать `connect → internet via tunnel → disconnect → routes restored`.
3. Документировать маршруты/исключения, которые нельзя корректно реализовать только Xray конфигурацией.
4. Писать собственный FFI к Wintun **только при доказанной необходимости**; не переписывать TUN, если Xray уже умеет то, что требуется.
5. Учитывать IPv4/IPv6, DNS, captive portals, network switching, Ethernet/Wi-Fi, несколько адаптеров и конфликт с другими VPN.

### 7.3. Маршрутизация и split tunnel

[ИСТОЧНИК] `split_tunnel.mode="exclude"`, поля `cidrs` и `domains`. Это не вполне определяет поведение пакетов.

[ПРОЕКТНОЕ ПРЕДЛОЖЕНИЕ] Зафиксировать семантику:

- Full tunnel — все целевые внешние IPv4/IPv6 маршруты идут в VPN, **кроме** bootstrap-маршрута к endpoint Xray (защита от петли), локальных исключений и системных критических адресов по политики.
- `exclude.cidrs` — CIDR должны обходить туннель; при конфликтующих/overlap CIDR алгоритм должен быть детерминирован.
- `exclude.domains` — нужен механизм сопоставления доменных имён DNS/IP/TTL и покрытия нескольких адресов/CDN; нельзя обещать полноценное domain-based исключение простой статической таблицей маршрутов.
- Смены DNS, IPv6 и адреса endpoint отрабатываются корректно.
- LAN bypass (принтер/NAS) только после решения OPEN-04 и тестов.
- Тесты не должны оставлять Windows машину без сети при падении процесса.

### 7.4. Kill switch

[БЛОКЕР OPEN-03] В оригинале вопрос о включении kill-switch в первом релизе не решён. Не подменять решение пустым checkbox или firewall-правилом.

Если утверждено — отдельная design review: Windows Filtering Platform / Windows Firewall rules, privilege model, исключения на issuer/DNS/endpoint, reboot safety, emergency recovery и официальный тест DNS/IPv4/IPv6 leakage. При выключенном kill-switch обязан работать безопасный network rollback. Нельзя рекламировать функцию, пока интеграционный тест не пройден.

### 7.5. Типы отказов

- Сервер недоступен; неправильный публичный REALITY key; порт недоступен; смена SNI; некорректный UUID; отзыв на сервере.
- Xray запущен, но TUN не создан; TUN создан, но нет дефолтного маршрута; DNS не отвечает; UDP работает/не работает; сеть переключилась.
- Процесс Xray падает; хранилище недоступно; невалидная политика; время Windows неверно; клиентская учётка заблокирована.
- Должны быть классифицируемые коды ошибок, backoff и восстановление сети с учётом kill switch policy.

## 8. Windows Service, storage, lifecycle

### 8.1. Service Control Manager

- Использовать `windows-service` (MIT OR Apache-2.0) или эквивалентные официальные Windows Rust bindings.
- Сервис должен выполнять SCM state transitions: START_PENDING/RUNNING/STOP_PENDING/STOPPED, stop controls, правильные таймауты.
- Startup type **Automatic**. Recovery options — по документированной политике, без бесконечного restart storm.
- Хранить состояние service отдельно от GUI. GUI должен уметь показать SERVICE_UNAVAILABLE и направить к администратору, а не запускать service с UAC самостоятельно.

### 8.2. Файловая модель

```text
%ProgramFiles%\ScrumeVPN\
   ScrumeVPN.exe
   ScrumeVPNSvc.exe
   xray.exe
   wintun.dll     [если требуется зафиксированным Xray-релизом]
   THIRD_PARTY_NOTICES.txt
%ProgramData%\ScrumeVPN\
   policy.json / policy.sig  [signed, service write]
   profile.json             [signed, protected]
   state\                    [protected, atomic update]
   logs\                     [redacted, rotated]
```

- Права: обычный сотрудник не может изменять `ProgramFiles` binaries и service state/policy/profile в `ProgramData`. Доступ на чтение sensitive профиля следует **не давать по умолчанию** даже если исходный SPEC говорит «только чтение»: в профиле UUID/REALITY параметры. Уточнить ACL до финального выпуска.
- Использовать `%LOCALAPPDATA%` / per-user DPAPI только там, где разрешено моделью secret ownership; никакой plaintext fallback.
- Атомарная запись `write temp → fsync/flush → rename` и recovery последнего валидного снимка.
- Смена учётки: отзыв/очистка локального секрета с учётом прав и server enrollment, корректный переход при работающем TUN.

### 8.3. Multi-user Windows

- Терминальная сессия/RDP, fast user switching: сервис глобален для компьютера, а enrolment может быть per-user. Это порождает конфликт: кто контролирует единственный глобальный VPN? **OPEN-09**.
- Минимум: описать поддерживаемую модель (один сотрудник на одном ПК или активный интерактивный пользователь); запрет смены владения туннелем без политики.
- Не допускается privilege escalation через IPC, включая инъекции path, аргументов Xray, config, SID.

## 9. MSI, обновление, развертывание

### 9.1. Выходные файлы

- `ScrumeVPN-1.0.0-windows-x64.msi` — целевой.
- `ScrumeVPN.exe`, `ScrumeVPNSvc.exe` в установленной директории, а не отдельно выдаваемая пользователю система.
- `checksums.txt` (SHA-256), `build-manifest.json`, `THIRD_PARTY_NOTICES.txt`, инструкции администратора и сотрудника, `RELEASE_NOTES.md`.
- `.iso` не делать. `.exe` installer типа NSIS допустим только **как дополнительная опция**, если заказчик её отдельно согласует.

### 9.2. Установка

- Использовать Windows WiX/MSI через Tauri custom template/fragment или отдельный WiX-проект, который делает всё нужное (не обещать, что штатный Tauri bundler сам всё настроит).
- ServiceInstall/ServiceControl или эквивалентные конструкции MSI: регистрация, правильные имена/DisplayName, старт, остановка, удаление, rollback при ошибке.
- Поставка Xray/wintun в установленную директорию; проверенная архитектура x64; лицензионные уведомления.
- Чистая установка, silent install (`msiexec /i ... /qn` для администраторского/GPO развёртывания), update/reinstall/repair, rollback, uninstall without orphan adapters/services/routes.
- Установка системного сервиса и TUN-драйвера требует **администраторских или эквивалентных делегированных прав**. Исходная фраза «установка без прав администратора у пользователя» означает, что IT развернёт MSI централизованно через GPO/Intune/admin context; стандартный пользователь сам не сможет установить service без elevation.
- Если отсутствует WebView2, отдельно отработать наличие/установку runtime и офлайн-сценарий.

### 9.3. Подпись

- Подпись EXE/MSI требует доступный code-signing сертификат, хранимый в защищённом signing workflow; запрет хранить сертификат в репозитории.
- Отсутствие подписи не значит, что SmartScreen всегда заблокирует; наличие сертификата не гарантирует полное отсутствие предупреждений/reputation. В QA различать unsigned test build и commercial signed release.
- Публикация: подписанные артефакты + checksums + SBOM/licenses + changelog.

## 10. Сборка с macOS и Windows CI

### 10.1. Рекомендуемая модель

1. macOS, VS Code и Codex: код, документация, Rust unit tests для platform-neutral crates, frontend dev, mock issuer.
2. GitHub Actions Windows x64 runner: компиляция Windows service и GUI, Tauri WiX/MSI, lint/test, публикация артефакта **в приватный workflow**.
3. Реальный Windows 11 x64 ПК или локальная/облачная VM: service installation, route/TUN/Wintun/DNS/kill-switch/E2E, сетевой rollback, reboot.
4. Windows 10 x64 — отдельно, только если заказчик продолжает требовать поддержку и принимает риск устаревшей ОС.

### 10.2. CI gates

**На PR:** `cargo fmt --check`, `cargo clippy -- -D warnings`, `cargo test --workspace` по доступным targets, frontend typecheck/test/build, лицензии и зависимости, secret scan, контрактные fixture tests, `cargo audit` при наличии и разрешённом network connectivity; Windows matrix compile.  
**На main/tag:** собирать reproducible manifest с фиксированными версиями; unsigned QA MSI; signed release только после approved signing flow; создавать SHA-256; публиковать внутренний отчёт о тестах.  
**Не:** запускать integration tests на реальном issuer без разрешения, помещать production token в GitHub Secrets только ради теста, публично публиковать артефакт, выводить приватные конфиги в CI logs.

### 10.3. Ограничения macOS

- macOS позволяет писать почти весь код, но не тестировать подлинный Windows service/SCM, HKCU Run, Named Pipes Windows, MSI, Wintun/route behavior.
- Официальная Tauri документация говорит, что **MSI собирается на Windows с WiX**; cross-compilation Windows NSIS с macOS возможна с оговорками, но не заменяет Windows E2E.
- Mac на Apple Silicon с Windows ARM виртуалкой **не равен** реальной целевой Windows x64. GitHub runner `windows-latest` способен обеспечить x64 сборку, а тесты kernel/network должны пройти на Windows x64.
- Код Windows-specific оборачивать в `#[cfg(windows)]`, тесты для остальных платформ не должны ломаться.

## 11. Производительность и масштаб 15–20 пользователей

[ИСТОЧНИК] Словесное требование: одновременно работать до 15–20 сотрудников. ТЗ не содержит измерения пропускной способности или целевой латентности. **Не гарантировать конкретные Mbps и не выбирать новый VPS без измерения**.

[ПРОЕКТНОЕ ПРЕДЛОЖЕНИЕ] Программа нагрузочных испытаний:

- Проверка выдачи 20 уникальных enrolment UUID и профилей через тестовый issuer.
- 20 параллельных (или staged) client sessions на реальном staging Xray/issuer, без disruption существующих четырех клиентов; если нет 20 рабочих Windows машин — симуляция серверных соединений на отдельном стенде плюс 2–3 реальных Windows client E2E.
- Тест revoke одного enrollment на фоне оставшихся активных сессий: новые подключения отозванного пользователя запрещены; чужие не разорваны.
- Одновременное profile refresh 20 клиентов с jitter; API не теряет изменения в JSON/DB.
- Фиксировать CPU/RAM/bandwidth, latency, error rate, потерю пакетов, DNS поведение.
- Целевые пороги (например, время соединения, Throughput, availability) **утверждаются отдельно** после измерения оборудования/канала.

## 12. План разработки для Codex: 12 ворот качества

**Запрещено начинать следующий этап, пока предыдущий не зафиксирован тестом/отчётом.** Каждая задача — отдельная ветка/commit и описание «что изменено / как проверено / что заблокировано».

### G0. Инвентаризация, requirements traceability

- Прочитать все источники, не менять код.
- Заполнить `docs/TRACEABILITY.md` (требование → компонент → тест → статус), `docs/OPEN_DECISIONS.md`, `docs/ADRs/`.
- Аудировать upstream refs/лицензии, источники релизных бинарников, activity, риски fork; зафиксировать лицензии и pinned versions.
- **Выход:** матрица и архитектурное заключение, без «уже выполнено».

### G1. Нейтральный каркас

- Создать monorepo Rust workspace + Tauri, чистое брендовое окно и navigation без внешних зависимостей по API.
- Fake service adapter / fake state; unit tests state machine.
- **Выход:** macOS `cargo test` и Tauri UI dev могут работать, но явно обозначены mock.

### G2. Windows service + IPC

- На Windows runner собирается service, SCM loop, protected pipe с DACL, ограниченная команда `status.get`, mock connect.
- Тесты: неавторизованный SID получает отказ, валидный SID получает status, oversized JSON отклоняется, stop safe.
- **Выход:** демонстрация на Windows x64; mock-функции помечены `NOT_IMPLEMENTED`.

### G3. Подписанные контракты

- JSON Schema + RFC 8785/выбранная каноникализация, Ed25519 test vectors Python↔Rust.
- Тесты invalid signature, modified expiry, replay, stale profile, wrong key, wrong protocol, malicious values.
- **Выход:** нет подмены данных даже при valid JSON.

### G4. Mock issuer ↔ GUI flow

- Тестовый локальный issuer со сценариями OTP/ошибок/rate-limit/revoke. **Не реальный прод**.
- Полный fake enrollment flow, renewal, переключение account. Решить browser flow/email OTP.
- **Выход:** код и логи не раскрывают секреты.

### G5. Xray TUN feasibility spike [КРИТИЧЕСКИЙ ПУТЬ]

- Отдельный тестовый сервер и Windows x64, pinned Xray + official Wintun.
- Минимум: IP route + DNS checks + reconnect + disconnect + crash cleanup.
- **Выход:** видео/логи/матрица результатов; если НЕ проходит — не строить коммерческую оболочку поверх прокси-мокапа.

### G6. Protected storage & service-owned tunnel

- Выбрать утвержденную модель DPAPI, service-only storage, child process supervision; GUI не управляет xray.exe напрямую.
- Тесты переподключения, потери DPAPI context, смены сессии, перезапуска службы.
- **Выход:** рабочее connect/disconnect по service IPC на тестовом профиле.

### G7. Реальная issuer integration в staging

- После утверждения API: `/vpn/profile`, signed enrollment, profile refresh, idempotent Xray AddUser / RemoveUser.
- Сравнить с Python issuer, поддержать старые endpoints и существующих клиентов.
- **Выход:** запись/отзыв конкретного тестового устройства, чужие сессии активны.

### G8. Политика, DNS, split tunnel

- Signed policy, refresh schedule, server-driven updates; DNS, CIDR exclude; domain-based exclusions только после доказанного алгоритма.
- **Выход:** network verification для IPv4/IPv6, Wi-Fi/Ethernet, LAN обход если approved.

### G9. Kill-switch [условно]

- После решения OPEN-03; иначе явно `not in release`, а не декоративная функция.
- Windows networking tests failure/reboot/uninstall.

### G10. Production UI + MSI

- Брендинг, трей, HKCU Run, one-instance, Windows SCM install via WiX, offline WebView2 behavior, admin deployment.
- **Выход:** один MSI ставится на чистую Win 11 x64 и удаляется без следов сетевой конфигурации.

### G11. Security review & regression

- Threat model, code review, supply-chain audit, protocol fuzz/invalid inputs, pipe ACL, secrets leakage, permissions, update/uninstall safety.
- **Выход:** список рисков, остаточные риски, подтверждение тестами.

### G12. Пилот и сдача

- 2–3 пилотных устройства, затем до 15–20 при готовом staging/prod change window.
- Admin handbook, user guide, release manifest, signed artifacts (если сертификат предоставлен), отчёт всех acceptance tests, known limitations и rollback.
- **Выход:** акт технической приёмки по чек-листу, не по внешнему виду GUI.

## 13. Требования к исходникам, качеству и безопасной работе агента

1. Писать читаемый код и тесты **вместе** с изменениями; не подменять тесты `assert!(true)`.
2. Все сетевые/Windows side effects спрятать за интерфейсами; platform-neutral ядро доступно для тестов на macOS.
3. Не использовать `unwrap()/expect()` на сетевых ответах, произвольных JSON или событиях пользователя без обоснования.
4. Fail closed на неправильную подпись/недопустимый профиль. При аварии сети восстанавливать маршруты в соответствии с политикой, без оставления непредсказуемых правил.
5. Не отключать TLS verification, антивирус или Windows firewall ради прохождения тестов.
6. Не писать bootstrap scripts с `curl | bash` для production без pinned version/checksum.
7. Не запрашивать и не сохранять в репозитории реальные `at-/as-/sk-`, коды из почты, Xray private key, signing private key, PFX сертификат.
8. Не передавать секреты через GitHub Issues, CI logs, файлы `.md`, скриншоты, GitHub Actions artifacts.
9. Для любой зависимости: repo URL, конкретный tag/commit, лицензия, usage, security caveat, update strategy.
10. При копировании third-party кода проверять LICENSE и совместимость **для конкретных файлов и вложенных зависимостей**. Без подтверждения — reference only, не copy.
11. Не копировать коды/ассеты Amnezia/NekoRay/Throne/Hiddify/v2rayN и GPL-licensed VPN клиентов. Можно изучать общие идеи архитектуры, не переносить код или UI.
12. Не заявлять, что сборка корректна, пока не пройдёт Windows CI и E2E; указывать честный `built / unit-tested / integration-tested / e2e-tested`.
13. Выдавать в каждом PR: краткое описание, список изменённых файлов, команды тестирования и результат, отклонения от ТЗ, новые риски, что делать далее.
14. Не деплоить серверные изменения, не менять `employees.json`, не добавлять/отзывать живых сотрудников без явного разрешения.
15. Использовать приватный репозиторий из-за информации о заказчике; хранить только тестовые значения. `SPEC_ORIGINAL.md` с реальными инфраструктурными подробностями **не должен автоматически попадать в публичный GitHub**.

## 14. Архитектурные решения и открытые вопросы (BLOCKER REGISTER)

| ID | Вопрос | Почему критично | По умолчанию до ответа |
|---|---|---|---|
| OPEN-01 | Email OTP из `/request`/`/verify` **или** браузерный device-code flow? | Разные контракты: endpoints не описывают настоящий OAuth device-code flow | Разработать mock OTP; сделать browser flow только после утверждения |
| OPEN-02 | Где хранится `at-…`: per-user DPAPI, machine vault/TPM? Подключение до логина? | SYSTEM не обязан иметь доступ к user DPAPI; автостарт до логина противоречив | Писать ADR, не обещать pre-login VPN |
| OPEN-03 | Kill switch нужен в v1? | Опасные сетевые правила, отдельная приёмка | Не включать в production до решения |
| OPEN-04 | Разрешён LAN bypass? Какие CIDR? | Принтеры/NAS/локальные ресурсы | Не угадывать исключения |
| OPEN-05 | Как согласовать `sk-…` из `/verify` и запрет его выдачи клиенту? | Выдача стороннего API-ключа нарушает принцип минимальных прав | Игнорировать, редактировать логи, предложить совместимый server-side VPN flow |
| OPEN-06 | Откуда берётся подписанный `policy.json`? Как доставлять admin push? | API для policy отсутствует | Проектировать `PolicyProvider`, без фиктивной remote admin реализации |
| OPEN-07 | Формат Ed25519 canonical payload и ротации ключей? | Иначе несовместимость Python/Rust и дыры подписи | Предложить JCS/RFC8785 + envelope; ждать решения |
| OPEN-08 | Семантика `split_tunnel.domains`, IPv6, DNS; допустима ли деградация? | Не все исключения решаются статическим CIDR | Тестировать, описывать ограничения |
| OPEN-09 | Один ПК = один пользователь? RDP/fast user switching? | Один глобальный SYSTEM tunnel и per-user secrets | Ограничить пилот моделью один пользователь на ПК |
| OPEN-10 | Кто выпускает и оплачивает сертификат подписи, какой signing flow? | Без этого не будет signed enterprise installer | unsigned QA MSI, чёткая маркировка |
| OPEN-11 | Как обновлять Windows 10 после EOL? Требуется ли ESU/LTSC? | Корпоративная безопасность | Win 11 primary, Win 10 compatibility target pending |
| OPEN-12 | Кто и когда предоставляет staging issuer/Xray и Windows машины? | Невозможна реальная E2E без стенда | mocks + CI, не считать приёмкой |
| OPEN-13 | Требуется ли корпоративная ссылка-активация/enrollment link? | Фраза про «ссылку» не согласуется с запретом настроек | Не добавлять импорт произвольных VPN ссылок |
| OPEN-14 | Приёмочные показатели: время коннекта, TTL после отзыва, 20 пользователей, QoS? | Нельзя измерить соответствие | Подготовить метрики и запросить threshold |
| OPEN-15 | Должен ли `/app-key` участвовать в VPN-profile retrieval? | Оригинал описывает оба токена, но `/vpn/profile` требует `at-…` | Придерживаться оригинального wire example до уточнения |
| OPEN-16 | Canonical profile + `expires_at`/policy signed envelope | Неподписанные expiry/версия допускают tampering/replay | Отложить production signing; формализовать контракт |
| OPEN-17 | Exact Xray version, TUN readiness and Wintun redistribution conditions | Встроенная TUN поддержка зависит от версии/параметров | POC на pinned stable release |
| OPEN-18 | Надёжное хранение UUID/aliases после рестарта issuer/Xray | Dynamic AddUser не равен персистентному источнику истины | Design reconciliation + restart tests |

Каждый пункт должен иметь: `owner`, `decision`, `date`, `evidence`, `impact`, `status` и ссылку на ADR/тест. Не допускать `implicitly resolved`.

## 15. Приёмочные сценарии в краткой форме

Полная версия в `docs/ACCEPTANCE_MATRIX.md`. Условия завершения:

- C-01: установка MSI на чистую Windows 11 x64 с admin/delegated context; служба зарегистрирована и работает.
- C-02: обычный пользователь запускает GUI без UAC и не может менять service/профиль.
- C-03: первый вход с допустимым email и кодом приводит к валидному enrollment; неизвестный сотрудник отклоняется.
- C-04: два устройства одного сотрудника получают разные UUID; повторный запрос одного устройства идемпотентен.
- C-05: подмена 1 байта профиля/signature/expiry → отказ до применения.
- C-06: реальный connected state после проверки TUN/routes/DNS, а не по факту запущенного `xray.exe`.
- C-07: системный трафик проходит по согласованному full/split tunnel, а endpoint не зацикливает маршрут.
- C-08: connect/disconnect, crash Xray и Windows reboot оставляют сеть в предсказуемом состоянии.
- C-09: GUI закрыто, сервис ведёт себя по политике; трей и статус корректны после нового запуска.
- C-10: отзыв одного enrollment запрещает его доступ, чужие устройства продолжают работать.
- C-11: service pipe не принимает команды от посторонней учётки; вход не даёт elevation.
- C-12: invalid/expired policy не применяется и не раскрывает секреты.
- C-13: silent install/upgrade/uninstall, включая отсутствие осиротевших драйверов/маршрутов и корректный rollback.
- C-14: тест 15–20 сотрудников (staging), metrics и наблюдения о реальном capacity.
- C-15: source, dependencies, licenses, notices, SHA, changelog, test report, admin/user manuals предоставлены.
- C-16: `Mac-only build` не считается выполнением тестов Windows service/driver/MSI.

## 20. Стоп-факторы сдачи

Не объявлять версию `1.0.0` готовой, если: нет Windows x64 E2E; нет работающего TUN; есть plaintext `at-…`; подписи не проверяются; доступ к SYSTEM pipe может получить неавторизованный юзер; Windows маршруты/DNS ломаются при отключении; revoke не запрещает доступ на шлюзе; установщик не удаляет службу; профили hardcoded; серверные изменения сделаны без согласования; чужие лицензии/бренд нарушены; профиль не выдаётся штатным корпоративным процессом.

**Итоговое инженерное задание:** разработать не демонстрацию интерфейса, а надёжный корпоративный Windows VPN-клиент с установщиком и управляемым доступом, используя существующий Xray и issuer как источники истины, сохраняя неизменность работающей инфраструктуры до согласованного внедрения.
